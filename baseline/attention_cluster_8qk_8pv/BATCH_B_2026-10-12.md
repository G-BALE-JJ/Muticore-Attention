# 批次 B：受控诊断与完整软件组合矩阵

后续启动实验发现 guest 诊断打印影响性能测量。本批数据保留为相同日志版本下的受控比较；最新干净性能基线及边界说明见 [STARTUP_RELEASE_2026-10-12.md](STARTUP_RELEASE_2026-10-12.md)，不能将两种 guest 的结果混为同一版本。

日期：2026-10-12。

## 实现与测量范围

本批次增加单选 `GOLEM_DIAGNOSTIC_ORACLE`，默认 `none`；无效名称拒绝运行。所有真实软件组合都使用 `none`，诊断数据不作为可部署性能结果。64 arrays、单 operand context、GM 容量、端口、DMA 配额和 SFU 数量保持正式基线配置。

| 名称 | 实际干预 | 保留的条件 / 解释边界 |
|---|---|---|
| `gm_read` | Projection input/weight operand 本地读服务为 0 cycles | 仍经现有 FIFO、端口、队列、回调与 generation；Norm/RoPE、partial、Attention 读取不变。不是整个系统所有 GM 读取为零 |
| `matrix_program` | Projection matrix broadcast 服务为 0 cycles | 原命令提交、单 operand 所有权、真实矩阵写入、队列、完成回调仍存在；Attention 编程不变 |
| `input_scatter` | Projection input scatter 服务为 0 cycles | 仍写入真实输入、保留命令/所有权/回调；Attention scatter 不变 |
| `weight_arrival` | 用同一 FP16 输入文件中的真实权重立即填入当前现有 GM slot | 按请求 tile 读取，不创建额外 resident weight bank；移除该供给的 HBM/NoC/landing 工作及其竞争，因此不是仅修改 HBM latency 的敏感性实验 |
| `worker_start` | 从 host 形状构建与真实 guest descriptor 相同的诊断描述符，在实测 baseline `chain_start_cycle` 统一启动 | 每个后续真实 guest descriptor 必须逐字节一致；所有 16 个 worker 的启动事件必须位于固定起点。诊断省去启动 skew，不是实现新的 guest release 优化 |
| `projection_barrier` | 所有 16 个 producer 真实完成后，经已有控制传输通知 manager，立即事件驱动提交已准备好的 Attention descriptor | 等真实输出/完成 ACK；保留原 descriptor、拓扑读取、worker 资源和控制传输。这测量全局就绪后的轮询/guest 提交空隙，不是按 head/tile 提前消费的收益上限 |
| `attention_barrier` | 同一 tick 内推进可就绪的 scheduler 状态，直到正常资源/数据 guard 阻止继续 | 不跳过 QK→softmax→PV 数据依赖、不增加 context/credit，不缩短真实计算服务。输出实际额外推进次数；若为 0，实验未观察到该类可压缩状态间隙，不能宣布所有 Attention 屏障不重要 |

零服务请求通过正常 self event 完成，保留提交和完成边界。忙碌区间并集不把长度为零的区间当成非法正长度预约。诊断与默认条件都必须检查数据；没有用缓存里的旧值或“尚未 ready 的值”替代 producer。

这些是明确范围内的受控干预。结果不能直接称为整个硬件的全局下界；不同 oracle 的节省不能相加。尤其两个 barrier case 收益低于 1% 时，只能暂停其具体轮询/提交路径，不能据此排除跨 head/tile 流水。

oracle 保留原调度，因此测量的是该调度下的敏感性，并非任意软件重排方案的严格收益上限。软件预取可能同时改变 command phase、提交时刻和其它资源等待；不能仅凭一个零服务 oracle 就把所有软件方案的收益限定在其差值内。

## 实验编排与可复现性

[`run_batch_b.py`](run_batch_b.py) 运行 15 个 case × 2 个正式序列长度，共 30 次：同一个 all-off baseline、7 个 oracle、完整 2³ 矩阵中另外 7 组。矩阵的 B 复用同批基线，不使用不同版本的历史数据替代。

三个因素为 input-pair prefetch、local-weight prefetch、array_groups=1/2（64 vs 32+32），完整 B/G/W/WG/I/IG/IW/IWG。矩阵输出三个主效应、三个二阶交互（按第三因素分层），以及三阶交互。主效应为跨其它因素的平均高低差；负值意味着缩短延迟，正的二阶交互意味着弱于独立节省之和。

每个 case 独立保存：

- 输入 SHA256、guest、两个共享库、关键源码、runner/分析器的 SHA256；
- 明确的 GOLEM 环境与命令（不继承调用 shell 的其它 GOLEM 实验开关）；
- 原始 MPI rank stdout/stderr、控制/phase 日志与资源 sidecar；
- 16 个 worker 的数据流、控制、资源时间和实际重叠；
- NumPy O 误差、资源拓扑/generation 验证、HBM layout 与基线 byte-exact；
- 原报告 E2E、固定 baseline origin 的 E2E、最后 O ACK→root 完成等待；
- baseline 的 phase 链 E2E 重建。

所有 oracle 关闭时若 E2E 与冻结参考变化，runner 立即停止。`worker_start` 采用同一批 baseline 的起点；其它 case 也按这个固定起点比较，以免干预导致起点移动。阶段 end 的计时定义继续采用最后 Attention worker completion，同时单列 O ACK/root 边界。

启用 `GOLEM_RESOURCE_TRACE_DOMAINS=gm,array,wcp,projection` 只过滤 trace 输出，保留所有资源的模拟。避免每个 case 产生数十 GiB 的 HBM/SFU per-request 日志；本批不重复声明 HBM/SFU细粒度覆盖。`analyze_resource_timeline.py --allow-filtered` 显式允许这一观测范围，其它区间、DMA 配对和最终 O ACK 校验仍执行。

`report_projection_e2e.py` 只在日志存在 projection-barrier oracle 标记时允许真实 descriptor 早于 guest flag wait 结束；原有 flag 数量、状态、projection 完成与 Attention 开始顺序、其它正确性检查继续保留。默认模式的同步顺序检查不放宽。

当前仍没有完整跨资源 DAG/slack；本批不会用累计资源服务量伪造 slack。每个 case 以真实模拟时序和输出作为诊断依据。

## 验证与复现

首次 small 同步启动诊断捕获了重复启动：最早 guest accept 比被报告的 job start 早一周期。修复为 accept 只校验/确认真实 descriptor，执行由统一起点触发；wait 在诊断启动前不能返回。失败产物保留在 `small_v1`，最终验证使用后续版本。

```bash
python3 baseline/attention_cluster_8qk_8pv/run_batch_b.py \
  --stage small --suite all --sequences 1024 \
  --artifact-root results/batch_b_small_reproduction

python3 baseline/attention_cluster_8qk_8pv/run_batch_b.py \
  --stage formal --suite all --sequences 1024 2048 \
  --reference-root results/retired_ws_final_verified \
  --artifact-root results/batch_b_formal_reproduction
```

`--resume` 只复用同一 SHA256 版本下已有 PASS 的完整 case；失败/半成品 case 不自动删除，改用新 artifact root 或明确处理失败目录。未完成队列的 summary 为 RUNNING，不能标为 PASS。

独立 case 可使用 `--case-names` 与 `--cpu-set` 分片，复用通过验证的 all-off baseline。宿主 MPI 核组只改变墙钟运行速度，不改变模拟硬件；它按物理核索引而非 SMT 逻辑 CPU 编号解释。首次两条队列用了超出 16 个物理核的索引，在仿真前被拒绝；失败日志保留，重试使用有效且互不重叠的核组。

可复现的并行入口 [run_batch_b_parallel.py](run_batch_b_parallel.py) 自动验证核组范围、重叠和完整 case 覆盖，先运行两组 all-off 基线，再用四个独立 subprocess 队列运行剩余 case；没有调用代理协作工具。完整重跑命令：

```bash
python3 baseline/attention_cluster_8qk_8pv/run_batch_b_parallel.py \
  --artifact-root results/batch_b_reproduction \
  --reference-root results/retired_ws_final_verified
```

本次实际分片产物：S1024 baseline 为 `formal_v2/baseline/s1024`，S2048 baseline 为 `formal_baseline_v3/baseline/s2048`；`reference_baseline/s1024,s2048` 指向它们。非 baseline 使用 `formal_s1024_a,b,c_retry,d_retry` 和 `formal_s2048_a,b,c,d`。S1024 baseline 与分片版本唯一允许的源码差异是 runner 新增 CLI 分片选项，模型/guest/共享库/其它源码均须相同。

[`summarize_batch_b.py`](summarize_batch_b.py) 校验 case 数量、唯一性、输入/库/源码身份、硬件契约、固定起点、输出检查，再对每个 case 重建 phase/control E2E。缺少任何 case 时拒绝发布完整因子效应；版本差异在每个 case 的机器汇总中显式列出。

[`analyze_batch_b_waits.py`](analyze_batch_b_waits.py) 另将排队/服务/可见等待裁剪到各 worker 的 Projection job，排除后续 Attention 使用相同资源产生的等待。MAC 利用率按实际参与的 32/64 个阵列加权，不把部分阵列延长的 busy union 当作整个阵列群利用率提高。

实现关联：[`diagnosticOracle.h`](../../src/sst/elements/golem/attention/diagnosticOracle.h)、[`test_batch_b.py`](test_batch_b.py)。完整正式结果汇总目标为 `results/batch_b_20261012/summary.json`；`formal_v2/summary.json` 是中途切换分片前的部分队列，不能用作完整结果。

## 如何解释本批次

零服务 oracle 消掉一个等待后，其它等待会重新暴露。例如 S1024 的 worker 16：本地读 phase 从 112,032 降至 7,584 cycles，但等权重到达的 phase 从 13,628 增至 90,293；matrix program phase 从 62,976 降至 3,072 时，等权重到达也增至 46,867。不能把原有 phase 时间全视为可兑现的端到端收益。

S1024 真实矩阵中，I/W/IW 在 Projection 窗口内的 GM 请求累计排队分别为 73,440 / 23,279 / 99,474 cycles（worker 16；基线 0）。预取允许先提交请求，同时也会争用同一个 GM 读端口。排队累计可以重叠，不能直接作为 E2E 损失；必须同时看完整 E2E 和真实服务重叠。

相同 worker 的阵列计算工作量在软件组合间保持 6,488,064 array-cycles。按参与阵列数加权，基线 MAC 利用率约 26.3%，IW 约 28.3%。计算量不变，改善来自更短的等待和调度窗口；不能用两组阵列的 busy union 延长来宣称所有阵列利用率翻倍。

`attention_barrier` 日志的 `scheduler_progress_passes` 只计所选状态键的变化，不覆盖所有内部提交/ready 变化。即使该计数为 0，额外调用也可能微调提交时间；S1024 的 E2E 差值为 5 cycles。这个诊断不能代替真正的跨 tile 数据依赖分析。

## 正式结果与决策

30/30 正式 case 和 15/15 small case 全部通过。两组默认基线保持 573,772 / 1,354,890 cycles；所有正式 case 的输出与基线逐字节一致，NumPy O 最大绝对误差均为 0.0001220703125。Golem 与 memHierarchy 编译/安装通过，56 项基线工具测试及 140 项 Attention 测试通过。

所有 case 保留原报告结束边界，oracle 使用各序列 baseline 的固定起点。以下 oracle 是诊断干预，不是可部署优化。

| Oracle | S1024 E2E | 节省 cycles | S2048 E2E | 节省 cycles |
|---|---:|---:|---:|---:|
| gm_read | 544,670 | 29,102 | 1,303,141 | 51,749 |
| matrix_program | 546,860 | 26,912 | 1,305,050 | 49,840 |
| input_scatter | 549,397 | 24,375 | 1,308,802 | 46,088 |
| weight_arrival | 559,536 | 14,236 | 1,330,398 | 24,492 |
| worker_start | 542,723 | 31,049 | 1,324,497 | 30,393 |
| projection_barrier | 571,724 | 2,048 | 1,353,996 | 894 |
| attention_barrier | 573,767 | 5 | 1,354,890 | 0 |

两个 barrier oracle 的范围只包括本文注明的轮询/提交间隙；不能把小收益外推为跨 head/tile 流水没有收益。

| 组合 | S1024 E2E | S2048 E2E |
|---|---:|---:|
| B | 573,772 | 1,354,890 |
| G | 549,023 | 1,310,006 |
| W | 547,822 | 1,305,331 |
| WG | 545,865 | 1,304,191 |
| I | 547,822 | 1,306,601 |
| IG | 544,908 | 1,304,166 |
| IW | 544,931 | 1,304,066 |
| IWG | 546,585 | 1,305,044 |

完整资源时间、交互效应、起点、输出检查和版本差异见同目录 JSON。

I=输入对预取，W=本地权重预取，G=既有 64 arrays 分为 32+32 两组；B 为三项关闭。两个序列均无新增 operand context、GM 端口或计算阵列。

选择 IW 作为后续优化的共同起点：S1024 为 544,931 cycles，节省 28,841（5.03%）；S2048 为 1,304,066 cycles，节省 50,824（3.75%）。S1024 的 IG 比 IW 快 23 cycles，但 S2048 慢 100 cycles，差距不足以支持增加阵列组调度复杂度。IWG 两组都慢于 IW（分别多 1,654 / 978 cycles）。本批不自动修改已有默认配置。

完整正交效应确认强交互：在 G=1 时，IW 二阶交互为 +23,059 / +47,024 cycles。这表示同时开启的节省远小于两个单项节省之和；正值不表示单项没有效果。三个主效应在两组均为负，但平均主效应也不能替代具体组合的 E2E。

下一步优先分别实现和验证：①缩短 worker 启动错峰，尤其集中准备/提交 guest 描述符；现有控制信号传播只有 9–25 cycles，不应先优化控制 link。②在现有单 GM 读端口和有界缓存内，按消费时刻安排 input/weight 预取，减少队列互相阻塞，而非盲目增加 outstanding。启动 oracle 的收益是在 all-off 调度上测得，不能直接加到 IW 的收益上，实际改动需要在 IW 上重新端到端对照。

跨 head/tile Projection→Attention 流水仍值得分析，但先补齐 producer/consumer 及资源争用的完整依赖 DAG。当前两个 barrier oracle 的小收益不足以否定这条路径，完整 DAG/slack 也未在本批完成。
