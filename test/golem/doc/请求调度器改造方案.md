# 请求调度器改造方案

## 目标

把当前

- `group ctrl` 做 task/stage 协调
- `worker` 自己发 `remote load`
- 数据直接回 `worker GM`

改成

- `group ctrl` 继续负责 task/stage 协调
- `manager request scheduler` 统一按 `tile/transfer` 发请求
- 数据仍然直接回 `worker GM`

目标不是让 manager 搬运数据，而是把无序请求注入改成受控请求整形。

## 总体结构

```text
worker
  -> 提交 transfer descriptor
  -> manager request scheduler
  -> scheduler 统一向 memory node 发请求
  -> memory node 直接把数据回到 worker GM
  -> worker 本地完成 ready/flag
  -> worker 向 group ctrl / scheduler 汇报完成
```

三层职责分离：

- `group ctrl`：谁做什么、什么时候进入下一阶段
- `request scheduler`：请求怎么发、哪个 node 先发、当前还能发多少
- `worker GM`：数据直收、落地、本地 ready

## 一、组件接口定义

## 1. GroupCtrl 保留接口

继续保留以下语义：

- task 分配
- 组内 ready/done/barrier
- worker 生命周期管理
- 高层阶段推进

建议继续保留的接口类别：

- `submit_task(core_id, task_id, ...)`
- `notify_worker_done(core_id, task_id, stage)`
- `notify_group_done(group_id)`
- `query_stage(group_id)`

不再负责：

- 直接控制 DMA 发起窗口
- per-node inflight 限流
- chunk 级 grant

## 2. ManagerRequestScheduler 新组件接口

建议新增组件：

- `golem.ManagerRequestScheduler`

建议提供两类接口。

### A. worker -> scheduler 提交接口

- `submit_transfer(const TransferDesc&)`
- `poll_transfer_status(request_id)`
- `notify_transfer_consumed(request_id)` 或 `notify_transfer_done(request_id)`

语义：

- worker 提交 tile/transfer 请求
- scheduler 返回 request_id 或接受确认
- worker 不直接发内存请求

### B. scheduler 内部调度接口

- `enqueue_transfer(node_id, desc)`
- `can_issue(node_id)`
- `issue_next(node_id)`
- `on_transfer_done(request_id)`
- `release_credit(node_id, amount)`

语义：

- 维护 per-node queue
- 维护 per-node credit / outstanding
- 完成后回收 credit

## 3. Worker 侧接口变化

worker 侧保留：

- 生成 tile/transfer 需求
- 检查本地 GM ready flag
- 数据到齐后启动 compute

worker 侧替换：

- 旧：`dma_remote_load_issue*()` / `remote_load()`
- 新：`submit_transfer_to_scheduler()`

## 4. memory-side 接口变化

memory-side 必须支持新的请求语义：

- 请求发起者是 manager scheduler
- 数据返回目标是 worker endpoint
- 数据写回地址是 worker GM 地址

因此需要支持：

- `return_endpoint`
- `return_addr`
- `request_id`

## 二、消息结构体字段

## 1. TransferDesc

建议字段：

```c++
struct TransferDesc {
    uint64_t request_id;
    uint32_t worker_core_id;
    uint32_t group_id;
    uint32_t target_node_id;
    uint64_t src_mm_addr;
    uint64_t dst_worker_gm_addr;
    uint32_t dst_worker_endpoint;
    uint32_t bytes;
    uint16_t kind;      // A tile / B tile / optional
    uint16_t priority;  // optional
};
```
```

最关键字段是：

- `target_node_id`
- `dst_worker_endpoint`
- `dst_worker_gm_addr`
- `bytes`
- `request_id`

## 2. SchedulerReadReq

manager 发往 memory node 的真正请求建议字段：

```c++
struct SchedulerReadReq {
    uint64_t request_id;
    uint64_t src_mm_addr;
    uint64_t return_addr;
    uint32_t return_endpoint;
    uint32_t bytes;
    uint16_t target_node_id;
    uint16_t kind;
};
```
```

语义：

- 由 scheduler 发出
- memory node 读取 `src_mm_addr`
- 数据返回 `return_endpoint`
- 写入 `return_addr`

## 3. SchedulerReadResp

memory node -> worker GM 的返回建议字段：

```c++
struct SchedulerReadResp {
    uint64_t request_id;
    uint64_t return_addr;
    uint32_t bytes;
    std::vector<uint8_t> data;
};
```
```

语义：

- 数据直接回 worker 的 endpoint
- worker GM 按 `return_addr` 落地

## 4. TransferDoneAck

worker 或 worker GM -> scheduler 的轻量完成确认：

```c++
struct TransferDoneAck {
    uint64_t request_id;
    uint32_t worker_core_id;
    uint16_t target_node_id;
    uint16_t status;
};
```
```

第一版建议由 worker 在本地检测到 ready 后发 ack 给 scheduler，用于归还 credit。

## 三、时序图

## 1. 当前机制

```text
worker
  -> remote.ld / dma_remote_load_issue
  -> GM 直接向 node 发请求
  -> 多 worker 并发无序注入
  -> memory node 回复
  -> completion 直接回 worker GM
  -> worker wait / retry / compute
```

问题：

- 请求入口是多源无序
- 回程 completion 容易在热点 node / 热列竞争
- 调度依据和真实瓶颈错位

## 2. 改造后机制

```text
worker
  -> submit_transfer(desc)

manager request scheduler
  -> enqueue into per-node queue
  -> check node credit
  -> issue SchedulerReadReq to memory node

memory node
  -> read src_mm_addr
  -> send SchedulerReadResp to worker endpoint

worker GM
  -> write data to dst_worker_gm_addr
  -> set local ready / flag

worker
  -> sees ready
  -> compute
  -> send TransferDoneAck to scheduler

manager request scheduler
  -> release node credit
  -> issue next transfer
```

## 3. 关键时序点

- `worker submit`：只提交 descriptor，不直接发内存请求
- `scheduler issue`：统一按 node 发请求
- `data return`：直接回 worker，不经过 manager
- `done ack`：只传轻量控制信息，用于归还 credit

## 五、实施顺序

## 阶段 1：最小可行版本

目标：验证“统一请求发射 + 数据直返”是否降低 tail。

做法：

- 新增 scheduler 组件
- worker 提交 transfer descriptor
- scheduler 按 node FIFO 发请求
- 每 node 固定 `credit=1~2`
- completion 直接回 worker GM
- worker ready 后发 done ack 给 scheduler

先不做：

- 动态 credit
- 复杂优先级
- 按字节计 credit

## 阶段 2：替换旧 grant 主导路径

目标：让旧 `GROUP_MAX_INFLIGHT_PER_NODE` 退居次要或失效。

做法：

- group ctrl 不再直接限制 DMA 发起
- scheduler 成为真正的 issue authority

## 阶段 3：策略增强

加入：

- per-node RR
- age-based scheduling
- A/B 请求分类
- starvation 防护

## 六、后续优化路径

## 1. credit 从 transfer-credit 升级到 byte-credit

第一版按 transfer 数管理足够验证方向。

后续建议：

- 按 `bytes` 扣 credit
- 更贴近返回路径真实压力

## 2. credit 从静态升级到动态

根据以下信号调整 node credit：

- completion 速率
- e2e latency
- local queue depth
- hotspot node utilization

这样可以让 scheduler 真正成为 completion-aware 调度器。

## 3. transfer 粒度进一步对齐计算粒度

从简单 tile request 继续演进到：

- A tile transfer
- B block transfer
- 多 tile 批次请求

但上层始终不要退回 chunk-visible。

## 4. scheduler 与 task mapping 联动

后续可把 task -> node 映射与 scheduler 联动：

- 分散热点 node
- 降低静态列热点

## 5. 增加 request/completion 统计闭环

新增观测项：

- submit -> issue 延迟
- issue -> first byte return 延迟
- issue -> transfer done 延迟
- per-node credit idle ratio
- per-node queue occupancy

这样才能判断瓶颈到底在：

- scheduler
- node return path
- NoC hotspot
- backend service

## 七、风险与原则

## 风险

- manager scheduler 自己成为 request bottleneck
- credit 太小导致 scheduler wait 替代当前 group wait
- transfer 粒度太大导致公平性差

## 必须坚持的原则

- manager 只进 request-plane，不进 data-plane
- 数据必须直接回 worker GM
- 调度粒度必须是 tile/transfer，不是 chunk
- credit 回收必须与完成绑定，而不是时间绑定

## 八、最终建议

最值得先做的不是复杂策略，而是先验证这个最小闭环：

- `worker submit transfer`
- `scheduler per-node FIFO issue`
- `data direct return to worker`
- `worker done ack returns credit`

如果这一版就能明显压低：

- `dma_timeout_retry_sum`
- `avg/max e2e rtt`
- `dma_wait_share`

那就说明方向正确；后续再加 credit 自适应和优先级策略才有意义。
