# WEE 本地状态化与事件驱动数据流执行改造计划（2026-04-15）

## 1. 目标

本计划的唯一核心目标是：

**让执行推进完全留在 WEE 本地，由事件自动触发，从而把 CPU / runtime / mailbox 从细粒度执行路径中拿掉。**

进一步目标包括：

1. 大幅降低 `issue_write`
2. 大幅降低 `sched_protocol`
3. 降低 `group_wait`
4. 让 `data_movement_time` 被 compute 尽可能隐藏
5. 让 `array_compute_active_time` 在总时间中占比明显上升

本计划不再围绕“如何更高效地写 mailbox”展开，而是直接切换执行范式：

- 从 `CPU 指令驱动`
- 切到 `WEE 本地状态 + 事件驱动`

## 2. 当前问题的本质

当前架构的结构性问题是：

1. 细粒度执行状态仍需要通过 GM / mailbox 表达
2. WEE 虽然已经接管了一部分执行，但仍偏串行状态机
3. DMA / load / compute / writeback 之间没有形成稳定流水
4. manager / runtime 仍保留部分启动、完成、协调职责

结果是：

- `issue_write` 居高不下
- `sched_protocol` 下降不明显
- `data_movement_time` 无法被 compute 隐藏
- `control_overhead_time` 继续主导总执行时间

## 3. 改造原则

### 原则 1：执行状态不写 GM

所有中间执行状态必须存于 WEE 本地成员变量，而不是通过 GM / mailbox 持久化表达。

### 原则 2：状态推进靠事件，不靠轮询协议

下一阶段触发应来自：

- DMA 完成事件
- buffer ready
- array 完成事件
- writeback slot 空闲

而不是：

- CPU 再发一条命令
- mailbox 某个 flag 被写 1

### 原则 3：GM 只承载数据，不承载细粒度控制

GM 保留用于：

- 输入 tile 缓冲
- partial sum / local accum store
- 最终输出
- 极少数 coarse completion

GM 不再用于：

- request submit
- request done
- per-k/per-step 状态位

### 原则 4：流水必须显式设计

WEE 不能只是“顺序执行的状态机”，必须是“显式多阶段流水执行器”。

## 4. WEE 中哪些状态必须留在本地

以下状态必须完全本地化，不能写 GM：

## 4.1 调度状态

- `bundle_active`
- `bundle_id`
- `task_index`
- `current_k`
- `next_k`
- `task_done_count`

## 4.2 buffer 生命周期状态

对于每个 buffer slot：

- `buffer.valid`
- `buffer.tile_k`
- `buffer.prefetch_issued`
- `buffer.prefetch_done`
- `buffer.load_done`
- `buffer.in_compute`
- `buffer.writeback_pending`
- `buffer.reusable`

## 4.3 array 执行状态

- `compute_inflight`
- `pending_array_count`
- `array_ready_mask`
- `array_done_mask`

## 4.4 writeback 状态

- `partial_sum_dirty`
- `result_materialized`
- `writeback_inflight`
- `writeback_done`

## 4.5 资源状态

- `dma_budget_remaining`
- `bundle_quota_remaining`
- `prefetch_window_occupancy`

这些状态全部应为 WEE 成员变量，不写 GM。

## 5. 哪些数据必须继续写 GM

虽然状态不应写 GM，但以下数据仍必须写 GM：

### 5.1 HBM / host -> local GM 的 DMA payload

因为 WEE 仍需通过 `GlobalMemory` / DMA engine 把远端数据拉到本地。

### 5.2 local accum store

如果一个 bundle 内复用 A tile、切换多个 `n_tile`，则 partial sum 需要从 array output buffer spill 到更大的本地累加层。

### 5.3 最终 C writeback

最终输出仍必须回到 host/HBM。

### 5.4 coarse completion flag

最终只保留：

- bundle/task 级完成标志
- worker finished 标志

而不保留细粒度 request/done 状态。

## 6. 事件驱动推进模型

## 6.1 核心事件类型

WEE 内部应围绕以下事件推进：

1. `PrefetchIssued(buffer_id, k_tile)`
2. `PrefetchDone(buffer_id, k_tile)`
3. `LoadReady(buffer_id, k_tile)`
4. `ComputeIssued(buffer_id, k_tile)`
5. `ArrayDone(array_id, buffer_id, k_tile)`
6. `ComputeDone(buffer_id, k_tile)`
7. `WritebackIssued(buffer_id, k_tile)`
8. `WritebackDone(buffer_id, k_tile)`
9. `TaskDone(task_id)`
10. `BundleDone(bundle_id)`

## 6.2 事件触发规则

### Rule A：Buffer 空闲且有剩余 `k_tile`

触发：

- `PrefetchIssued`

### Rule B：A/B 两路 DMA 都完成

触发：

- `LoadReady`

### Rule C：LoadReady 且 array 空闲

触发：

- `ComputeIssued`

### Rule D：所有 array done

触发：

- `ComputeDone`

### Rule E：若非最终轮，则 buffer 回收；若为最终轮或需 spill，则进入 writeback

触发：

- `WritebackIssued`

### Rule F：一个 task 的所有 `k_tile` 完成

触发：

- `TaskDone`

### Rule G：bundle 中所有 task 完成

触发：

- `BundleDone`

## 7. 真正的双缓冲流水设计

## 7.1 Buffer 结构

推荐定义：

```text
BufferSlot {
  id
  tile_k
  task_id
  mat_local_addr
  vec_local_addr
  prefetch_done
  load_done
  compute_done
  writeback_done
  reusable
}
```

最小实现使用两个 slot：

- `buffer0`
- `buffer1`

## 7.2 时间重叠目标

目标稳态：

```text
buffer(next): prefetch
buffer(cur):  compute
buffer(prev): writeback
```

如果只做双缓冲，则先实现：

```text
buffer(next): prefetch
buffer(cur):  compute
```

writeback 尽量后移到 compute 间隙或 bundle 尾部。

## 7.3 为什么这会降低 `data_movement_time`

因为当前数据搬运之所以大，是因为它直接暴露在关键路径上。

双缓冲后：

- `k+1` 的 DMA 在 `k` 计算时进行
- 只要 DMA 不比 compute 慢太多，就能被部分或大部分隐藏

## 8. 让 compute 成为主导的关键机制

## 8.1 A tile 常驻 / 复用

如果 bundle 设计为同一 `m_tile` 下多个 `n_tile`，则：

- `A(m_tile, k_tile)` 应在本地尽量常驻
- 同一个 A tile 尽量只 DMA 一次
- 后续多个任务共享

## 8.2 partial sum 留在本地 accum store

array output buffer 只服务当前活跃 tile，不适合作为 bundle 内多个 `n_tile` 的长期结果驻留区。

因此需要：

- `local accum store`

作为 bundle 级 partial sum 层。

### 注意

这不是核间规约，只是本 worker 私有的 partial sum spill / reload。

## 8.3 延迟 writeback

不要每次 `k_tile` 都写 host/HBM。

建议：

- 中间 partial sum 保留在 local accum store
- 最终 task/bundle 尾部统一 writeback

## 9. 要删除的旧路径

当新数据流路径稳定后，必须删除以下路径，不能长期并存：

### 9.1 worker 本地 request submit ring

删除原因：

- 它是 `issue_write` 的主要来源之一

### 9.2 worker 本地 done ring

删除原因：

- 它是 `sched_protocol` 的主要来源之一

### 9.3 runtime 对 load/compute 的显式发射

删除原因：

- 它违背数据流驱动原则

### 9.4 per-k/per-step mailbox 状态位

删除原因：

- 状态推进应改为 WEE 本地成员变量

## 10. 实施步骤

## Phase 1：本地状态完全内存化（组件内）

1. 清点所有仍写 GM 的中间状态
2. 改为 WEE 本地成员变量
3. 只保留数据和 coarse completion 写 GM

目标：

- 直接打 `issue_write`

## Phase 2：双缓冲 prefetch/compute overlap

1. 引入 `buffer0/buffer1`
2. 支持 `next-k prefetch` 与 `current-k compute` 并行
3. 先不做复杂 writeback overlap

目标：

- 直接打 `data_movement_time`

## Phase 3：延迟 writeback + local accum store

1. 中间结果不立即写回 host/HBM
2. 先落到 local accum store
3. task/bundle 尾部统一 materialize

目标：

- 进一步降低 `data_movement_time`
- 降低控制路径参与

## Phase 4：manager 只保留 quota / bundle dispatch

1. 删除 request/pair 语义
2. 只保留 coarse task/bundle 分发
3. coarse completion 直接回 manager

目标：

- 打 `sched_protocol`
- 打 `group_wait`

## 11. 预期收益

按阶段推进，预期收益应呈现：

### 阶段收益 A：本地状态内存化

- `issue_write` 明显下降

### 阶段收益 B：双缓冲 overlap

- `data_movement_time` 明显下降
- `avg_throughput_ops_per_cycle` 上升
- `array_utilization_pct` 上升

### 阶段收益 C：延迟 writeback

- `data_movement_time` 继续下降
- `control_overhead_time` 下降

### 阶段收益 D：quota dispatch 收口

- `sched_protocol` 下降
- `group_wait` 下降

## 12. 结论

要实现真正的数据流驱动计算，关键不是继续优化 CPU 如何发命令，而是：

1. 把所有中间执行状态留在 WEE 本地
2. 用事件自动推进下一阶段
3. 让 GM 只承载数据，不承载细粒度控制
4. 让双缓冲流水隐藏 DMA
5. 让 coarse completion 取代细粒度协议

只有这样，`issue_write` 才会真正消失，`data_movement_time` 才可能被 compute 覆盖，计算才有机会成为执行主导项。
