# 从 CPU 指令驱动切换到数据流驱动的执行架构设计（2026-04-15）

## 1. 问题定义

当前架构的根本问题，不是单个子组件慢，而是：

- 执行推进仍然由 CPU/runtime 高频指令控制
- worker 本地执行仍然需要依赖 mailbox/request/done 等协议动作推进
- manager 仍然过度参与执行细节

其结果是：

- 计算只是被触发的对象，而不是执行链的中心
- `issue_write`、`sched_protocol`、`task_desc`、`group_wait` 长期高位
- 数据搬运与计算难以形成稳定流水

因此，本设计的目标不是继续优化 mailbox 细节，而是：

**把执行从 CPU 指令驱动，切换到本地数据流驱动。**

这里的“数据流驱动”指：

- CPU 只下发粗粒度任务描述
- 本地执行引擎根据数据 ready、buffer 空闲、执行单元空闲等条件自动推进
- 中间不再通过 CPU/runtime/mailbox 表达每一步的执行意图

## 2. 核心设计原则

### 2.1 CPU 退出细粒度执行推进

CPU / runtime 只负责：

1. 构造任务图 / 任务列表
2. 配置执行参数
3. 提交 coarse descriptor
4. 等最终结果

CPU 不再负责：

- 每个 request 的提交
- 每个 `k_tile` 的显式发射
- 每次 DMA 完成后的下一步动作
- 每次 batch compute 的显式等待/继续

### 2.2 执行引擎按数据依赖自动推进

worker 节点内新增/升级本地执行引擎（WorkerExecutionEngine, WEE），负责：

- 取任务
- 发起 DMA prefetch
- 等待数据 ready
- 发起 batch load
- 发起 batch compute
- 发起 writeback
- 维护局部状态

WEE 的推进依据不是 CPU 指令，而是：

- DMA done
- buffer ready
- array idle
- writeback slot free

### 2.3 mailbox 从执行路径退出

mailbox 不再用于：

- per-request submit
- per-request done
- per-k-tile 协议推进

mailbox 未来仅保留为：

- coarse task queue / descriptor queue
- coarse completion queue

也就是说：

- 它不再表达“下一步做什么”
- 只表达“有哪些任务”与“哪些任务完成了”

### 2.4 manager 只定义资源边界，不定义执行步骤

manager 的职责应降级为：

- quota 发放
- coarse dispatch
- 粗粒度完成回收

manager 不再决定：

- 第几个 `k_tile` 现在能不能发
- 哪次 DMA 现在能不能发
- 哪次 batch compute 什么时候开始

这些都应由 WEE 本地根据数据和资源状态自动决定。

## 3. 新的职责边界

## 3.1 CPU / Runtime 该做什么

CPU 只应该做以下事情：

1. 生成 `TaskBundle` 或 `TaskListHeader`
2. 初始化 worker task queue
3. 启动某个 worker 的执行引擎
4. 等最终结果 / 完成标志
5. 做结果校验和统计归档

CPU 不该再做：

- 每轮 `k_tile` 的 DMA submit
- 每轮 `k_tile` 的 load / compute / wait 调用
- 每次 completion 的 publish / consume

### 设计要求

- CPU 发出的控制必须是 coarse-grain 的
- CPU 不能出现在高频执行关键路径中

## 3.2 本地执行引擎该做什么

本地执行引擎（WEE）应完全承担以下职责：

1. 读取 task / bundle header
2. 在本地推导 tile 地址与任务映射
3. 触发 DMA prefetch
4. 跟踪 DMA 完成
5. 触发 local GM -> array load
6. 触发 batch compute
7. 管理中间结果驻留 / spill / writeback
8. 聚合 task/bundle 完成
9. 最终只发布 coarse completion

### 设计要求

- WEE 是 worker 节点内唯一的执行推进者
- WEE 不依赖 CPU 来决定下一步
- WEE 只依赖本地状态与数据 ready 条件推进

## 3.3 manager 该做什么

manager 只承担：

1. quota dispatch
2. worker 资源准入
3. memory node / bandwidth 约束
4. coarse completion 回收

manager 不承担：

- request/pair 生命周期
- 单 task 内部执行节奏
- per-k-tile 级推进控制

## 4. 数据 ready 如何驱动下一阶段

这是从 CPU 驱动切换到数据流驱动的核心。

## 4.1 状态推进不靠显式命令，靠事件条件

WEE 每个周期或每次事件处理时，都根据以下条件推进：

### 条件 A：prefetch slot 空闲
- 若有待处理 task/tile
- 且 DMA 预算允许
- 则发起下一轮 DMA prefetch

### 条件 B：某 tile 的 A/B 数据 ready
- 则触发该 tile 的 batch load

### 条件 C：array idle 且 load 完成
- 则触发 batch compute

### 条件 D：compute done 且 writeback 资源可用
- 则执行 writeback 或本地 partial sum materialize

### 条件 E：bundle 中所有 tile 完成
- 则发布 coarse completion

## 4.2 用 ready-bit / local state 而不是 mailbox 值表达状态

建议 WEE 内部维护：

- `prefetch_ready[buffer_id]`
- `load_ready[tile_id]`
- `compute_inflight[tile_id]`
- `writeback_pending[tile_id]`
- `bundle_done`

这些状态存在 WEE 本地组件内，不写 GM mailbox。

GM/内存只承载：

- 真正的数据
- 最终 coarse completion flag

## 5. 推荐的数据流执行模型

## 5.1 目标模型

理想执行链路应是：

```text
TaskBundle ready
  -> next tile prefetch
  -> tile data ready
  -> batch load
  -> array compute
  -> result retained / delayed writeback
  -> next tile continues
```

而不是：

```text
CPU command
  -> DMA submit
  -> wait
  -> CPU command
  -> load
  -> CPU command
  -> compute
  -> wait
  -> next
```

## 5.2 流水阶段

WEE 内部建议至少有四个逻辑流水阶段：

1. `Prefetch`
2. `Load`
3. `Compute`
4. `Writeback`

并通过双缓冲或多缓冲实现：

- `k+1 prefetch`
- `k compute`
- `k-1 writeback`

## 5.3 A tile 常驻与结果延迟输出

为了最大化数据流驱动效果：

- A tile 尽量常驻并复用
- 输出 partial sum 尽量保留在本地 accum store
- 非最终阶段不立即写回 host/HBM

也就是说：

- 数据一旦进入本地，尽量在本地连续消费
- 控制流不打断数据流

## 6. 如何把 mailbox 从执行路径中拿掉

## 6.1 先删除 worker 本地 submit/done ring 的职责

这些 ring 当前的作用是：

- 表达细粒度 request
- 表达细粒度 done

在新架构里应被替换为：

- coarse task queue
- coarse completion queue

## 6.2 manager 与 worker 之间只保留 coarse 信号

worker 与 manager 之间只应保留：

1. `TASK_BUNDLE_DISPATCH`
2. `QUOTA_GRANT`
3. `BUNDLE_DONE`

除此之外的控制语义，都应在 worker 本地解决。

## 6.3 执行状态不再写 GM mailbox

不要再用 GM 写：

- 当前进度
- 当前 request 状态
- 当前 batch 状态

这些都应是 WEE 内部本地状态。

只有最终需要跨组件或跨节点观察的状态，才写回外部可见结构。

## 7. 迁移步骤

## Phase A：职责边界固定

1. CPU 只发 coarse descriptor
2. manager 只发 quota / bundle
3. WEE 成为唯一执行推进者

## Phase B：删除旧 worker submit/done 协议

1. worker 本地 request/done ring 退出执行路径
2. 只保留 coarse completion

## Phase C：WEE 流水化

1. prefetch / load / compute / writeback 重叠
2. 双缓冲 / 三缓冲
3. A tile 常驻复用

## Phase D：manager quota 化

1. 删除 request/pair 语义
2. 转为 quota / bundle dispatch

## 8. 预期收益

如果这套数据流驱动架构真正落地，预期：

### 直接下降

- `issue_write`
- `sched_protocol`
- `task_desc`
- `group_wait`

### 直接上升

- `avg_throughput_ops_per_cycle`
- `array_utilization_pct`

### 结构性变化

- `control_overhead_time` 不再主导
- `data_movement_time` 被流水化部分隐藏
- `array_compute_active_time` 在总时间中占比明显上升

## 9. 结论

要让计算成为主导，关键不是继续优化 CPU 如何更高效地发命令，而是：

1. 让 CPU 从细粒度执行推进中退出
2. 让 manager 从 request 级审批中退出
3. 让 worker 本地执行引擎根据数据 ready 自动推进
4. 让 mailbox 从执行路径退出，只保留 coarse 任务与完成语义

这就是从“CPU 指令驱动”切换到“数据流驱动”的本质。
